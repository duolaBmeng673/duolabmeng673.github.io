## Web 攻击技术

### 一、Web 应用体系脆弱性

**1. 三个层面的漏洞**
- 客户端（浏览器）漏洞
- Web 服务器漏洞
- Web 应用程序漏洞

**2. Web 本身的特点**
- **HTTP 无状态**：攻击无需模拟会话，单个请求即可发起攻击；
- **Cookie 包含敏感信息**：用户名、权限等，可被窃取或伪造；
- **数据库可能保存攻击代码**：如存储式 XSS。

**3. 主动攻击 vs 被动攻击**

| | 主动攻击 | 被动攻击 |
| --- | --- | --- |
| 方式 | 直接攻击 Web 服务器 | 设置陷阱，用户浏览即中招 |
| 目的 | 篡改或破坏目标数据 | 悄悄收集信息 |
| 影响 | 引发系统异常或故障 | 对系统无明显破坏，难以发现 |
| 典型 | SQL 注入、目录遍历、OS 命令注入 | XSS、CSRF、HTTP 消息头注入 |


### 二、Cookie 脆弱性与欺骗

**1. Cookie 的作用与工作过程**
1. 为了解决 HTTP 无状态问题，保存状态信息；
2. 用于辨别用户身份、会话跟踪，是保存在用户本地终端上的一些数据；
3. Cookie 由 server 生成，发给 client，浏览器将其保存在文件内，需要时再发给 server；
4. server 利用 Cookie 中的信息维护状态，从而判断 HTTP 传输中的状态。

**2. Cookie 结构**

```text
Set-Cookie: sid=abc123; Expires=Wed, 01 Jan 2030 00:00:00 GMT; Path=/; Domain=example.com; Secure
```

| 字段 | 含义 |
| --- | --- |
| `NAME=VALUE` | 名称与值 |
| `EXPIRE=DATE` | 过期时间 |
| `PATH=PATH` | 适用的 URL 路径 |
| `DOMAIN=DOMAIN_NAME` | 对应域名；不指定更安全，指定易留隐患 |
| `SECURE` | 是否仅在 SSL/TLS 下传输 |

> 补充：`HttpOnly` 属性可禁止 JS 读取 Cookie，能降低 XSS 窃取 Cookie 的风险。

**3. 脆弱性**
- Cookie 中含敏感信息（用户名、口令、权限、计算机名、访问网站记录等）；
- Cookie 存放在客户端，用户或攻击者可以读取、修改。

**4. Cookie 欺骗**：伪造 Cookie 信息，绕过网站验证。

```text
正常：Cookie: username=alice; role=user
伪造：Cookie: username=admin; role=admin     ← 网站若直接信任 Cookie 中的权限，就被绕过
```

**5. 防范**
- Cookie 中**仅存储会话 ID**，数据本身存放在服务器端；
- 或不使用 Cookie，改用 **Token 令牌机制**（如 JWT）。


### 三、SQL 注入攻击

**1. 定义**：将精心构造的 SQL 命令插入表单、域名或页面请求的查询字符串中，欺骗服务器执行，实现：
- 非法访问数据库内容；
- 篡改数据；
- 绕过认证；
- 运行程序、编辑文件。

**2. 漏洞成因：动态拼装 SQL**

```php
$name = $_POST['name'];
$pwd = $_POST['pwd'];

$sql = "SELECT * FROM users WHERE name='" . $name . "' AND pwd='" . $pwd . "'";
```
1.  从请求中获取用户名和密码。
2.  将用户名和密码拼接到 SQL 字符串中。
3.   把拼接完成的 SQL 语句交给数据库执行。
-  用户输入被直接拼进 SQL 语句，其中的单引号等符号会改变 SQL 的结构；
- 输入 `name = admin'--`：

```sql
SELECT * FROM users WHERE name='admin' -- ' AND pwd='...'
'--' 之后的内容被注释掉了，密码判断条件从 SQL 的有效语句中消失，因此密码判断失效，绕过认证
```

- 输入 `pwd = ' or '1'='1`：条件恒真，同样可绕过认证。

> 与格式化字符串漏洞同理：**用户输入（数据）被当成了指令（SQL 结构）**。

**3. 防护措施**

| 防护措施 | 内容 | 作用 |
| --- | --- | --- |
| 长度限制 | 只允许指定长度范围的输入（如用户名 8~20 位） | 阻止长 SQL 注入字符串 |
| 特殊字符转义 | 对 `'`、`--`、`_`、`%` 等 SQL 相关符号进行转义 | 防止拼接的 SQL 语法被破坏 |
| 类型/格式化校验 | 如 id 强制转换为 int | 防止非预期 SQL 结构注入 |
| 参数化查询/存储过程 | 不拼接 SQL，使用预编译 SQL | **从根本上消除** SQL 注入风险 |
| 低权限数据库账户 | 不使用 root/sa/admin | 限制攻击影响范围 |
| 敏感信息加密/Hash | 密码等不明文存储 | 防止数据泄露后被直接利用 |
| 异常信息隐藏 | 不向前端暴露数据库错误 | 防止攻击者获取系统结构信息 |
| 防护 XSS | 防止脚本注入与身份伪造 | 防止间接攻击后台 |
| 服务端校验 | 所有输入必须在服务端验证 | 防止绕过客户端校验 |

**答题版**

> SQL 注入是攻击者将精心构造的 SQL 命令插入表单、URL 查询字符串等输入中，利用程序动态拼装 SQL 且未检查输入的漏洞，欺骗服务器执行恶意 SQL，从而非法访问或篡改数据库内容、绕过认证，甚至运行程序。防范方法：检查并过滤用户输入中的单引号、双引号、分号等特殊字符；使用参数化 SQL 而不是动态拼装；遵循最小特权原则；减少返回的错误提示信息。

> 用户输入被拼进 SQL → 数据变成指令；参数化查询让输入永远只是数据。

### 四、XSS 跨站脚本攻击

**1. 定义**：将恶意代码（HTML 和客户端脚本，如 JS）注入到网页内容中，其他用户访问时浏览器自动执行，**以受害者身份运行**。

**2. 两个前提**
1. Web 程序必须接受用户输入（URL 参数、表单字段、HTTP 头部、Cookie 值）；
2. Web 程序会重新显示输入内容，且浏览器将其解释为 HTML 标记。

**3. 三种形式**

| 形式 | 恶意代码在哪 | 触发方式 |
| --- | --- | --- |
| 反射式（URL） | 在 URL 参数里，服务器不存储 | 受害者点击构造好的恶意 URL，脚本随响应返回并执行 |
| 存储式（持久性） | 保存到服务器数据库中 | 被显示给受害者时执行，所有访问该页面的用户都受影响 |
| DOM 式 | 修改页面 DOM 节点数据 | 前端脚本把输入写入页面时执行（补充：恶意数据可不经过服务器） |

**4. 反射式 XSS 攻击流程**（Alice 访问 Bob 的网站，Charly 为攻击者）

| 步骤 | 过程 | 说明 | 攻击关键点 |
| --- | --- | --- | --- |
| 1 | Alice 访问 Bob 网站并登录 | 网站保存用户敏感信息 | 正常登录环境 |
| 2 | Charly 发现反射型 XSS 漏洞 | 网站未过滤用户输入 | 存在输入输出漏洞 |
| 3 | 构造恶意 URL 并发送给 Alice | URL 中嵌入脚本代码 | 利用 URL 参数注入 |
| 4 | Alice 点击恶意链接 | 在已登录状态下访问 | 携带合法身份（Cookie） |
| 5 | 脚本在浏览器执行 | 服务器原样返回输入内容 | 浏览器执行恶意 JS |
| 6 | 信息被窃取并发送给攻击者 | Cookie/账户信息泄露 | 造成数据泄露与劫持 |

**5. 存储式 XSS：将恶意脚本保存到服务器数据库中**

| 步骤 | 过程 | 关键点 |
| --- | --- | --- |
| 1 | 攻击者在留言、评论等输入点提交含脚本的内容 | 输入点未过滤 |
| 2 | 服务器把内容存入数据库 | 恶意代码被持久保存 |
| 3 | 其他用户访问包含该内容的页面 | 无需点击特殊链接 |
| 4 | 服务器从数据库取出内容并输出到页面 | 原样输出，未编码 |
| 5 | 浏览器执行脚本，窃取 Cookie 等信息 | 影响所有访问者，危害更大 |

**6. 防范**
- 对用户输入的所有内容进行**过滤或编码**（如把 `<` 转为 `&lt;`）；
- 对输入的 HTML 内容做**白名单**检查；
- Cookie 设置 `HttpOnly`；使用 CSP（内容安全策略）。

**答题版**

> XSS 是攻击者将恶意脚本注入到网页中，其他用户访问时浏览器自动执行，从而以受害者身份窃取 Cookie、劫持会话等。前提是 Web 程序接受用户输入，并把输入内容重新显示在页面上，浏览器将其解释为 HTML 标记。分为反射式、存储式和 DOM 式。防范方法是对用户输入进行过滤或编码，并对 HTML 内容做白名单检查。

> 输入被当作 HTML/脚本输出 → 在受害者浏览器里执行。

### 五、CSRF 跨站请求伪造【重要】

**1. 定义**：攻击者伪装成受信任用户发送恶意请求。用户在未退出、未清理 Cookie 的情况下访问恶意网站，恶意网站诱导浏览器向目标网站发请求，浏览器**自动携带**用户的 Cookie，目标网站误以为是用户本人操作。

**2. 攻击流程**（用户 C、存在 CSRF 漏洞的网站 A、恶意网站 B）

| 步骤 | 过程 | 说明 |
| --- | --- | --- |
| 1 | 用户 C 登录网站 A（A 存在 CSRF 漏洞） | 浏览器保存 A 的 Cookie |
| 2 | 网站 A 验证通过 | Cookie 表示用户已登录 |
| 3 | 用户 C 访问恶意网站 B（未退出 A） | 攻击开始 |
| 4 | 网站 B 诱导浏览器请求网站 A | 伪造请求（如转账/修改密码） |
| 5 | 浏览器自动携带 Cookie 访问 A | **Cookie 自动附带（关键点）** |
| 6 | 网站 A 误认为是用户操作 | 执行请求 |
| 7 | 攻击成功 | 用户 C 被"代操作" |

**3. 防御**

| 防御措施 | 核心内容 | 作用 |
| --- | --- | --- |
| 短会话 + 退出机制 | 设置短暂登录会话，操作完成后退出并清除 Cookie | 降低会话被滥用的时间窗口 |
| 操作前二次验证 | 每次敏感操作（转账/改密）重新验证用户身份（如重新输入密码） | 防止伪造请求被直接执行 |
| 避免客户端保存敏感信息 | 不在浏览器保存用户名/密码等登录信息 | 防止被恶意网站利用 |
| CSRF Token 机制 | 每个请求附加随机（一次性）令牌进行验证 | 确认请求确实来自合法页面 |
| 修复 XSS 漏洞 | 消除跨站脚本漏洞 | 防止 CSRF 与 XSS 联动攻击 |
| 检查 HTTP Referer | 检查请求来源地址 | 拒绝来自其他网站的请求 |

**Tips**：Referer 用于携带请求来源地址，常用于反爬虫和防盗链，HTTP 标准将其拼写为 `referer`（少一个 r）。

**4. XSS 与 CSRF 对比**（补充）

| | XSS | CSRF |
| --- | --- | --- |
| 是否注入脚本 | 需要，恶意脚本在受害者浏览器中执行 | 不需要，只是让浏览器发出伪造请求 |
| 利用的信任 | 用户对网站的信任 | 网站对用户浏览器（Cookie）的信任 |
| 关键点 | 输出未编码 | Cookie 自动携带，且无法区分请求来源 |
| 核心防御 | 过滤输入、编码输出 | CSRF Token、二次验证 |

**答题版**

> CSRF 是攻击者诱导已登录目标网站的用户访问恶意网站，由恶意网站让用户浏览器向目标网站发出伪造请求。由于浏览器会自动携带目标网站的 Cookie，目标网站误以为是用户本人的操作而执行请求（如转账、改密）。防范方法：使用一次性 CSRF Token 并保证其安全、敏感操作要求重新输入密码、检查 HTTP Referer 头、设置短会话并及时退出。

> 浏览器自动带 Cookie + 服务器分辨不出请求来源 → 用户被"代操作"。

### 六、目录遍历

**1. 定义**：攻击者通过构造文件路径，访问到 Web 根目录之外的文件。

**2. 条件（三条同时满足）**
1. 允许外界指定文件名；
2. 允许使用绝对/相对路径指定其他目录的文件名；
3. 未对拼接后的文件名进行校验即允许访问。

**3. 防范**
- 避免外界指定文件名；
- 文件名不包含目录路径；
- 限制文件名仅包含字母和数字。

### 七、操作系统命令注入

**1. 原因**：应用程序调用 Shell，而 Shell 允许连续执行多条命令。

**2. 代码示例**

```php
system("ping -c 1 " . $_GET['ip']);
```

```text
?ip=127.0.0.1; cat /etc/passwd     ← 分号后的命令也会被 Shell 执行
```

**3. 防范**
- **不调用 Shell**（用语言自带的 API 代替）；
- 外部输入字符串不能作为命令行参数；
- 对特殊字符（`;`、`&&`、管道符等）进行转义。


### 八、HTTP 消息头注入

**1. 原因**：基于外部参数生成 HTTP 响应头时，攻击者通过**换行**（CRLF，`%0d%0a`）插入任意响应头或消息体。

**2. 危害**
- 生成任意 Cookie；
- 重定向到任意 URL；
- 执行 JS 代码，实现 XSS 效果。

**3. 代码示例**

```php
header("Location: " . $_GET['url']);     // 外部参数直接进入响应头
```

```text
?url=http://a.com%0d%0aSet-Cookie:%20sid=attacker
                  ↑ 换行后，攻击者插入了一个新的响应头
```

**4. 防范**
- 不将外部参数直接作为 HTTP 响应头输出；
- 使用会话变量转交 URL，由专门 API 处理重定向或生成 Cookie；
- 严格检查 HTTP 头中的换行符；
- 不使用 URL 直接指向重定向目标。


### 九、速查表

| 攻击 | 类别 | 根本原因 | 核心防御 |
| --- | --- | --- | --- |
| **Cookie 欺骗** | — | Cookie 存放在客户端并含敏感信息 | Cookie 只存会话 ID，或改用 Token |
| **SQL 注入** | 主动 | 用户输入被拼接进 SQL | 参数化 SQL、过滤输入、最小特权 |
| 目录遍历 | 主动 | 允许外界指定文件名且未校验 | 不让外界指定文件名 |
| OS 命令注入 | 主动 | 调用 Shell，可连续执行多条命令 | 不调用 Shell、转义特殊字符 |
| **XSS** | 被动 | 用户输入未编码就输出，被浏览器当 HTML 解释 | 过滤/编码输入、白名单 |
| **CSRF** | 被动 | 浏览器自动带 Cookie，服务器无法区分请求来源 | CSRF Token、二次验证、检查 Referer |
| HTTP 消息头注入 | 被动 | 外部参数进入响应头，换行未检查 | 不直接用外部参数、检查换行 |

> Web 攻击的共同根源：**不可信的用户输入没有经过检查，就被当作"指令"（SQL、HTML/JS、Shell 命令、文件路径、HTTP 头）使用**。
